## P0 — 必須在 Phase 2 之前決定

### P0-1 架構邊界自相矛盾：bot 是否可直連 DB？

**Codex 發現**：
- plan.md:36、plan.md:92 宣稱「bot 不得 import `src/services/*` 或 `src/db/*`，
  編譯期即檢查」
- 但 plan.md:311 的 Files to Create 又列 `src/bot/state.ts # bot_user_state
  DB ops (bot 唯一允許碰 DB 的地方)`

這兩條自撞。若 bot 直連 DB，未來 auth / project 驗證 / audit / transaction
邏輯會分裂兩套。

**建議（二選一，v1.3 定死）**：

| 選項 | 優點 | 代價 |
|---|---|---|
| **A. 全走 HTTP**：`GET/PUT /api/bot/state/:telegram_user_id` | 唯一寫路徑；未來多 bot 易擴 | bot 首次啟動前 API 需先 live |
| **B. 承認 bot 有受控 DB**：`bot_user_state` 是 bot-owned 唯一表 | 啟動順序解耦 | 破壞「唯一通道」原則宣稱 |

**我的初步推薦**：**A**。`bot_user_state` 只有 upsert 和 get，HTTP 成本極低；
且我們要求 `MCP → service` 也必須走 service，保持一致性。

### P0-2 memory undo / idempotency 不可靠

**Codex 發現**：
- `tasks.idempotency_key` 已經 UNIQUE（Phase 1 已上線）
- 但 `project_memories` 不改 schema，計畫把 key 塞 `metadata.idempotency_key`
- 無 unique index → webhook retry / Telegram 重送仍會雙寫；JSONB scan 非原子
- `DELETE /api/memories/by-idempotency/:key` 10 秒內撤銷完全不可靠

**建議（v1.3 二選一）**：

| 選項 | 說明 |
|---|---|
| **A. 加正式 column**：`project_memories.idempotency_key text UNIQUE` + partial index，與 `tasks` 一致 |
| **B. MVP 拿掉 memory undo**：只留 `tasks` undo；memory 靠 Phase 5 retrieval eval 確認沒亂寫再加 |

**我的初步推薦**：**A**。加一個 nullable text column + partial unique index
成本極低，而且一致性模型不分裂。

### P0-3 BOT token 無真正 project ACL

**Codex 發現**：
- plan.md:216 寫 BOT_API_TOKEN 有「`PATCH /api/tasks/:id` 限自己 project」
- 但 server 端沒有可驗證的「自己 project」身分來源
- bot 持有的是**全域 token**，不是 per-project token
- 目前實際等於「任意專案皆可讀寫」，名義上的 ACL 是假象

**建議（v1.3 三選一）**：

| 選項 | 語意 | 實作 |
|---|---|---|
| **A. 受信單用戶模型** | bot token = trusted single-user；不假裝 per-project ACL | 刪 spec 裡「限自己 project」字眼 |
| **B. 綁 telegram_user_id** | 所有 bot request 帶 `X-Telegram-User-Id`，server 查 `bot_user_state` 決定 active project | 多一層 header + server-side lookup |
| **C. token 綁 allowed_projects** | 每個 bot token 鎖定專案清單 | 需 token → project 表，超綱 |

**我的初步推薦**：**B**。bot 端已經要管 `telegram_user_id`，加個 header
成本小，且「未選拒寫」原則能從 server 端強制。

## P1 — Phase 1/2 間決

### P1-1 `search_feedback` 平行陣列缺 invariants

無 CHECK 保證 `result_ids` / `result_project_ids` / `rank_positions` / `scores`
長度一致，也沒保證 `selected_rank ∈ 1..N`。兩週後 retrieval eval 可能被髒
資料污染。

**行動**：Phase 2 service 層補 application-level 驗證 + 可選的 DB CHECK：

```sql
ALTER TABLE search_feedback
  ADD CONSTRAINT search_feedback_arrays_same_length
  CHECK (
    cardinality(result_ids) = cardinality(result_project_ids)
    AND cardinality(result_ids) = cardinality(rank_positions)
    AND (scores IS NULL OR cardinality(scores) = cardinality(result_ids))
  );
```

`selected_rank` 必屬於 `1..cardinality(result_ids)`：service 層驗證（SQL
expression 涉及 array 比對麻煩）。

### P1-2 project_id 優先序違反直覺

v1.1 寫 `CLAUDE.md marker > CC_MEMORY_PROJECT_ID > basename`，但 env var 看
起來該是 override。且現有 `src/utils/project-id.ts` 根本沒實作 env。

**行動（v1.3 改成）**：
```
(1) 明示 function 參數 explicit（最高）
(2) env CC_MEMORY_PROJECT_ID（override）
(3) CLAUDE.md marker（專案預設）
(4) 目錄 basename（fallback）
```

### P1-3 task PATCH 無併發控制

v1.1 沒定義 optimistic locking。兩 client 同時 `open → done` 會覆蓋
`completed_at`。

**行動**：Phase 2 service 層 `updateTask(id, patch, { expectedStatus })`，
SQL `UPDATE ... WHERE id = ... AND status = ?`，affected=0 時 throw。
MVP 不引入 version column，以 status 檢查代替。

### P1-4 UUID prefix 碰撞

`/done <id前6>` 2+ 筆同 prefix 時誤操作。

**行動**：Phase 4 bot 實作 `resolveTaskByShortId(prefix)` 規則：
- 0 筆 → 回「not found」
- 1 筆 → 執行
- 2+ 筆 → 列候選，要求更長 prefix
